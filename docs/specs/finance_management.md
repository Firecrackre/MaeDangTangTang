# 재정 관리 기획서

> 로비 허브 진입점은 `lobby_hub.md` 참조. 상환금·판매가 수식과 얽히므로 `pricing_calculation.md`를 함께 본다.
> 위험 거래(대장 기술)의 상환 이자 증가와 정합성을 유지한다 → `blacksmith_upgrade.md`.

---

## 1. 재정 관리

재정 관리는 플레이어의 메소 운용을 담당하는 로비 기능이다.

재정 관리는 크게 두 가지 기능으로 구성한다.

- 메소 대출 서비스
- 골드리치 은행 저축

메소 대출 서비스는 필수 구현 기능으로 본다.

골드리치 은행 저축은 가능하면 구현하는 후순위 기능으로 본다.

---

## 2. 메소 대출 서비스

메소 대출 서비스는 플레이어가 큐브와 무기를 모두 살 돈이 없을 때 사용할 수 있는 위기 대응 기능이다.

플레이어는 상환 부담을 크게 늘리는 대신, 일정 금액의 메소를 즉시 지급받을 수 있다.

### 사용 조건

메소 대출 서비스는 다음 조건을 만족할 때 사용할 수 있다. (구현: `GameManager.UpdateCanLoan`)

- 아이템(무기) 미보유 시: 상점의 모든 무기 슬롯을 실효 구매가(가격 협상 반영) 기준으로 구매할 수 없음
- 아이템(무기) 보유 시: 큐브(이상한 큐브)를 구매할 돈이 부족함
- 현재 게임 오버 상태가 아님
- 대출 사용 가능 횟수가 남아 있음 (한 게임당 1회)

즉, 플레이어가 다음 행동을 할 수 없을 정도로 메소가 부족할 때만 사용할 수 있다.

---

## 3. 메소 대출 서비스 효과

메소 대출 서비스 사용 시 다음 효과가 발생한다. (구현: `GameManager.RequestLoan`)

- **지급 메소 = 현재 상환 필요 메소**(`GetCurrentRepayment()` — 미납 상환금이 있으면 그 금액, 없으면 다음 단계 상환금 미리보기)를 즉시 지급
- **같은 금액이 빚(`Debt`)으로 누적** — 상환 시점에 `상환금 + 빚`을 한 번에 청구
- 대출 사용 횟수 증가 (`LoanUseCount`)

### 확정안

- 지급 메소: 현재 상환 필요 메소만큼 (고정값 아님, 동적)
- 빚 증가: 지급 메소와 같은 금액 (`Debt += 지급액`)
- 사용 제한: 한 게임당 **1회** (`BlacksmithConfig` `loan.maxUses = 1`)

예시: 이번 주 상환금이 45,000이면 → 45,000을 지급받고 빚 45,000이 쌓여, 상환 시점에 총 **90,000**을 갚아야 한다.

> 참고: 초기 기획안이었던 "고정 100,000 지급 / 상환금 2배 증가" 방식은 폐기되었다.
> 수치는 플레이 테스트를 통해 조정한다.

---

## 4. 메소 대출 서비스 흐름

메소 대출 서비스 흐름은 다음과 같다. (구현: `FinanceManager` + `HudManager`)

1. 진입: 상단 HUD의 대출 유도 슬라이드 팝업('대출하러 가기!') 클릭, 또는 로비에서 '재정 관리' 선택
2. 대출 서비스 센터(재정 관리 화면) 표시 — 지급액·늘어나는 빚·남은 횟수 안내
3. '대출하기' 버튼 선택
4. 경고 확인 팝업 표시
5. 플레이어가 대출 확정('대출받기')
6. 메소 즉시 지급 + 같은 금액 빚 누적
7. 재정 관리 화면 자동 닫힘 → 이전 화면으로 복귀

대출은 강력한 위기 탈출 수단이지만, 상환 시점에 빚까지 함께 청구되어 상환 부담을 크게 늘리기 때문에 신중한 선택이 필요하다.

대출 횟수를 모두 소진한 뒤에는 '대출하기' 버튼 위에 잠금 오버레이가 덮이며, 클릭 시 보드 흔들림 + 에러음만 재생되고 대출은 실행되지 않는다.

---

## 5. 메소 대출 서비스 경고 문구

대출 사용 전에는 플레이어에게 리스크를 명확히 안내한다.

예시 문구:

> “메소 대출을 받으면 지금 필요한 상환금만큼 메소를 즉시 받을 수 있지만, 같은 금액이 빚으로 쌓여 상환 시점에 한꺼번에 갚아야 합니다. 정말 대출을 받으시겠습니까?”

버튼 (구현: `ConfirmPopup`):

- 대출받기 (→ `RequestLoan` 실행)
- 취소 (팝업만 닫음)

> 참고: 초기 기획안의 "대출받기 버튼 2개(선택지 없는 연출)" 안은 폐기되었고, 실제 구현은 대출받기 + 취소 2버튼이다.

---

## 5-1. 상환액 스케줄 (주차별 상환금 — SSOT)

한 주 = 큐브 **주차별 N회** 사용(해당 주 최대 도달 = 상환 시점). 상환 주기는 주차별로 다르다 —
`debtCycles = {5, 6, 6, 7, 7}`, 조회 `GetDebtCycle(week)`. (⚠ 과거 고정 `debtCycle = 5` 방식은 폐기)

| 주차 | 사용 가능 큐브 수(상환 주기) |
| --- | --- |
| 1주 | 5회 |
| 2·3주 | 6회 |
| 4·5주 | 7회 |

상환액은 아래 표를 따른다. (구현: `BlacksmithConfig.mlua` `debtTable`·`debtGrowth`, 조회 `GetDebtAmount(stage)`)

| 주차(상환 단계) | 상환액 |
| --- | --- |
| 1주 | 45,000 메소 |
| 2주 | 70,000 메소 |
| 3주 | 100,000 메소 |
| 4주 | 140,000 메소 |
| 5주~ (표 밖) | **직전 주 × 1.1 (매주 10% 증가)**, 1,000 단위 반올림 |

- 표 범위(1~4주)는 고정값, 표를 벗어나는 주차부터 매주 10%씩 증가한다(`debtGrowth = 1.1`).
- 위험 거래(대장 기술) 보유 시 실효 상환금은 여기에 이자 %가 추가로 곱해진다(`ComputeRepayment`).
- ⚠ 과거 "5단계 이후 매주 +40,000(debtStep)" 방식은 폐기.

### 승리 조건

**상환 5회 성공(`DebtStage >= winStage = 5`, 즉 5주 경과) 시 승리**한다. 승리 시 승리 UI(최종 메소/사용 큐브/판매 횟수/최고 판매가 + 다시 하기)가 표시되고, 게임 플레이 액션(구매/큐브/판매/대출)은 모두 거부된다. (구현: `GameManager.RequestSettleDebt` 성공 분기 → `IsVictory`, UI는 `VictoryManager` + `ui/VictoryGroup.ui`)

## 5-2. 다음주 정산 팝업 (상환 연출)

상환 시점(N/N, N = 주차별 상환 주기) 도달 시 스크래치 화면에서는 **큐브 재사용·큐브 구매가 잠기고 판매만 가능**하다. 무기를 판매(또는 파괴 확인)하고 로비로 복귀하면 **다음주 정산 팝업**이 열린다. (구현: `NextWeekManager` + `ui/NextWeekGroup.ui`, 서버 정산은 `RequestSettleDebt` 단일 호출)

연출 순서:

1. 배경 딤 + 중앙 박스: 보유 메소 / 상환액 표시 (+ 빚 > 0이면 빨간 '빚' 줄)
2. 약 1초 후 보유 메소가 상환액만큼 **숫자 스크롤로 차감**
3. 빚이 있고 갚을 수 있으면 빚도 0으로 스크롤 후 **페이드아웃**
4. 상환액이 **다음 주 금액으로 스크롤 상승** (매주 10% 증가 체감 구간)
5. 팝업이 닫히고 다음 주 시작. 5주 완료면 승리 UI로 전환

정산 실패(게임오버) 분기:

| 상황 | 연출 | 게임오버 원인 |
| --- | --- | --- |
| 보유 메소 < 상환액 | 메소 0까지 차감 연출 → **상환액 2초 깜빡임** → 게임오버 UI | "상환액을 갚지 못하였습니다" |
| 상환액은 가능, 상환액+빚은 불가 | 메소 0까지 차감 → 빚 일부 감소 연출 → **빚 2초 깜빡임** → 게임오버 UI | "빚을 갚지 못하였습니다" |

> 실패 시 서버는 메소를 실제로 차감하지 않는다(게임오버 기록의 최종 메소 보존). 차감 연출은 클라이언트 표시 전용.

## 5-3. 대출 소진 후 구매 불가 = 스턱 게임오버

대출(1회)을 이미 사용한 상태에서 다음 상황이 **다시** 발생하면 게임오버다. (구현: `GameManager.CheckStuckGameOver`)

**판정 시점 (중요)**: 무기 미보유("weapon") 판정은 **플레이어가 무기 상점 화면을 열어 슬롯이 표시된 시점**에만 수행한다 — 로비/정산 직후에는 판정하지 않는다(로비에서 즉시 게임오버 금지, 유저 확정). 클라(`WeaponShopManager`)가 상점 표시/재추첨 시점에 `RequestShopStuckCheck`를 호출하면 서버가 권위 판정한다. 무기 보유("cube") 판정은 기존대로 큐브 사용/무기 구매 직후(스크래치 화면 컨텍스트) 서버가 판정한다.

| 상황 | 판정 기준 | 게임오버 원인 |
| --- | --- | --- |
| 무기 미보유 | 현재 상점 3슬롯 전부 실효 구매가 > 보유 메소 (새로고침은 디버그 전용이라 고려 안 함) | "무기를 살 돈이 부족합니다" |
| 무기 보유 | 이상한 큐브 살 돈 부족 **그리고** 지금 팔아도(보유 메소+판매 예상 수익) 상점 최저가 미달 | "큐브를 살 돈이 부족합니다" |

> 무기 보유 시 판매로 살아날 수 있으면 게임오버가 아니다 — 판매 후 미보유 판정이 이어서 잡는다(억울한 게임오버 방지).

연출: 대출 유도 슬라이드 팝업이 내려온 뒤 → **팝업 위에(팝업과 동일한 320×74 영역) X자 쇠사슬 2줄이 낙하해 걸쳐지고, 그 위로 자물쇠가 떨어져 착지**(각각 철컹 효과음) → 이후 게임오버 UI가 하늘에서 떨어져 바닥에서 튀며 등장. (구현: `GameOverManager` 사슬 시퀀스 + `HudManager.SetForceLoanPopup`. 사슬·자물쇠는 HudGroup `LoanPopup`의 자식 `LockOverlay` — 팝업 슬라이드 위치를 자동 상속)

### 게임오버 UI 공통

- 배경 딤 + 중앙 박스가 **낙하+바운스**로 등장 (모든 UI 위, GroupOrder 60)
- 표시: 모은 메소 / 사용한 큐브 수 / 사망 원인(4종) / 다시 하기 버튼
- 다시 하기 → `RequestRestart`(서버 전체 리셋, DataStorage 누적 기록은 보존)

## 6. 골드리치 은행 저축

골드리치 은행 저축은 플레이어가 보유 메소 일부를 은행에 맡기고, 매일 일정 비율의 이자를 받는 기능이다.

해당 기능은 게임의 진행 길이와 구현 범위에 따라 선택적으로 구현한다.

### 기능 목표

- 여유 메소를 가진 플레이어에게 추가 선택지 제공
- 모든 메소를 큐브에 쓰지 않고 일부를 보관하는 전략 추가
- 시간이 지날수록 이자를 통해 추가 수익 제공

---

## 7. 골드리치 은행 저축 흐름

골드리치 은행 저축 흐름은 다음과 같다.

1. 로비에서 재정 관리 선택
2. 골드리치 은행 저축 선택
3. 저축할 메소 금액 입력 또는 선택
4. 보유 메소에서 저축 금액 차감
5. 저축 메소에 금액 추가
6. 하루가 지날 때마다 이자 계산
7. 필요 시 저축 금액 출금
8. 출금한 메소를 보유 메소에 추가

---

## 8. 골드리치 은행 저축 기준안

골드리치 은행 저축 기준안은 다음과 같다.

- 최소 저축 금액: 10,000 메소
- 이자율: 하루 5%
- 출금 제한: 없음
- 저축 가능 횟수: 제한 없음
- 이자 지급 시점: 하루가 지날 때

해당 수치는 게임의 하루 진행 속도에 따라 조정한다.

게임이 짧게 끝나는 구조라면 이자율을 높이고, 게임이 길게 이어지는 구조라면 이자율을 낮춘다.

---

## 9. 재정 관리 표시 정보

재정 관리 화면에서는 다음 정보를 표시한다. (단, 보유 메소·상환금·상환 진행도는 로비/상점/스크래치 **공용 상단 HUD**(`HudGroup`/`HudManager`)로 표시된다.)

- 현재 보유 메소 (공용 상단 HUD)
- 현재 상환금 (공용 상단 HUD '상환 필요 메소')
- 상환 진행도 = 이번 주 큐브 사용 n/N (0→N, 상환 시점 N/N — '남은 개수' 감소식 아님. N = 주차별 상환 주기 5/6/6/7/7)
- 대출 가능 여부 (횟수 소진 시 잠금 오버레이)
- 대출 시 지급 메소 (= 현재 상환 필요 메소, 동적 갱신)
- 대출 시 늘어나는 빚 (= 지급 메소와 같은 금액, 동적 갱신)
- 남은 대출 가능 횟수
- 현재 저축 메소
- 예상 이자
- 출금 가능 금액

골드리치 은행 저축을 구현하지 않는 경우, 저축 관련 정보는 표시하지 않는다.

> 구현 현황: 대출 관련 3줄(지급액/늘어나는 빚/남은 횟수)은 `FinanceManager` 보드에 구현됨.
> 골드리치 은행 저축은 후순위 — 현재 `BlacksmithConfig`의 `savings` 수치(최소 10,000 / 하루 5%)만 준비되어 있고 로직·UI는 미구현.
